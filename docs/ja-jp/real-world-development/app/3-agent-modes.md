最初のレッスンでは、プロジェクトに小さな機能を追加しました。より大きな変更には、さらにしっかりしたプロセスが必要です。GitHub Copilot app は組織で既に使われている開発フローに沿って動作するため、適切なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスに沿って、新機能を追加します。Issue を使って機能を生成し、コードの妥当性と機能の動作を確認した後、プロジェクトにマージします。

> [!NOTE]
> 機能の開発を続ける間、同じセッションを使います。通常は、作業するファイルの種類ごとに異なるセッションや PR を使用しますが、ここでは基本概念に集中できるよう、手順を簡略化します。

このレッスンでは、次の操作を行います。

- GitHub Issue から新しいエージェントセッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザーキャンバスで機能を手動で検証します。

この機能の開発を続けながら、リポジトリの指示を更新し、既存の `quality-checks` スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、訪問者はカテゴリーやパブリッシャーでゲームを絞り込む必要があります。バックログの Issue には機能が記載されていますが、複数カテゴリーを組み合わせる方法など、コーディング前に合意が必要な詳細があります。Plan モードで判断を確定し、Autopilot に範囲を限定した実装を許可します。

## 背景

AI コーディングエージェントを開発フローに導入しても、基本は変わりません。むしろ、基本に沿うことがいっそう重要になります。多くの開発者は、次のような流れで作業します。

1. 必要な作業の詳細を記載した Issue を開きます。
2. 構築する内容を計画します。
3. コードを実装してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. pull request (PR) を作成します。
7. コードのレビューと継続的インテグレーションが成功したら、コードをマージします。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、ほとんどの場合は上記の流れに沿っています。

この標準的な進め方を守ることで、AI が生成したコードが要件を満たし、手作業で書いたコードと同じレビュー工程を通るようにできます。

## セッションモード

**セッションモード**は、エージェントにどの程度の自律性を与えるかを制御します。プロンプト欄の下にあるドロップダウンで設定でき、いつでも変更できます。

- **Interactive**: エージェントと一緒に作業します。エージェントは変更を提案し、次に進む前に入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントがコードの作成、テストの実行、反復作業を自律的に進め、入力を待ちません。

まず Plan モードで計画をレビューし、その後 Autopilot に実装させます。

## Issue からセッションを開始する

開始する前に、星評価の PR がマージ済みで、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys リポジトリのフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これは事前に用意された Issue なので、新たに作成する必要はありません。
2. **New session** を選択し、更新済みの `main` を基にした **new working tree** を選択します。

    ![New session ボタンを矢印で示した GitHub Copilot app の Issue ビュー](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モード選択で **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションで見つからない場合は、アプリの PATH またはバージョンマネージャーの設定を確認し、アプリを完全に終了してから再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで、npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てることで、Copilot がコードを書く前に、進め方をレビューできます。Issue から開始したため、Copilot は機能リクエストを既にコンテキストとして把握しています。次の内容を送信します。

```plaintext
この機能を実装してください。
```

Copilot の質問に回答し、計画を Issue の受け入れ条件と比較します。カテゴリーとパブリッシャーでの絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認します。複数カテゴリーをどう組み合わせるか、該当するゲームがない場合にどうするかなど、不明な動作について話し合います。

計画には、プロジェクト既存のツールを使った lint、ユニットテスト、E2E テスト、型チェックを含めます。フィルター機能の実装とテストに集中し、品質ワークフローを完了するまでは PR を作成しないでください。承認前に計画の変更を依頼し、後で検証できるよう Issue の URL と合意した明確化事項を控えておきます。

## Autopilot を明示的に承認する

計画に問題がなければ、**Approve and implement this plan**、または使用中のバージョンで相当するオプションを選択します。承認によってモードが自動的に切り替わると思い込まず、現在のモードを確認します。モード表示が **Autopilot** になっていることを確かめます。

Copilot が実装を開始します。承認済みの計画に沿って反復し、コードを生成してテストも実行します。

> [!NOTE]
> 承認すると、すぐに実装が始まる場合があります。先に計画をレビューしてください。依存関係が不足している、またはポートが競合していると Copilot が報告した場合は、チェック完了と判断する前にセットアップの問題を解決します。自分が起動したサーバーだけを停止してください。

## 実装をレビューして検証する

コードをマージする前にレビューします。ほかのコードと同様に、変更内容とサイトの動作の両方を確認しましょう。

1. **Changes** を開き、フィルター機能の実装とテストを調べます。
2. 複数カテゴリーやパブリッシャーの組み合わせを含め、結果を Issue と承認済みの明確化事項に照らし合わせます。変更が既存のリポジトリ指示に従っていることも確認します。
3. lint、ユニットテスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 失敗を解決し、該当するチェックを再実行してから実装を受け入れます。Playwright の E2E 設定はプレビューをビルドして実行し、ローカルサーバーを再利用する場合があります。テスト対象のサーバーが以前のレッスンのものではなく、この worktree のものであることを確認します。

## 新機能を試す

コードに問題がなさそうでも、実際に動くか確認しましょう。前のレッスンと同じようにアプリを起動し、ブラウザーキャンバスで開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザーキャンバスで開くよう Copilot に依頼します。

    ```plaintext
    アプリを起動して、ブラウザーキャンバスで開いてください。
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーウィンドウが開きます。
3. カテゴリーを選択し、結果が一致することを確認します。フィルターを解除してからパブリッシャーを選択し、結果がそのパブリッシャーに一致することを確認します。
4. カテゴリーとパブリッシャーのフィルターを組み合わせ、結果を Issue と承認済みの計画と比較します。複数カテゴリーに対応している場合は、合意した組み合わせの動作を検証します。
5. 結果が0件になる組み合わせを試し、空の状態を確認します。フィルターを解除またはリセットして、一覧全体が戻ることを確認します。
6. 終了したら、次のプロンプトを使って、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    開発サーバーを停止し、ブラウザーキャンバスを閉じてください。
    ```

## 次のレッスンに向けてセッションを保持する

まだフィルター機能の PR を作成したり、マージしたりしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを使います。次はフィルター機能のコードにカスタム指示を適用し、スキルと QA の改善を追加してから、レッスン 8 でまとめた PR を作成してマージします。開発サーバーを停止した後は、セッションをアイドル状態にしておき、次のレッスンで同じセッションに戻れます。

## まとめと次のステップ

複数のエージェントモードを使って機能を構築し、レビューしました。このレッスンでは、次の操作を行いました。

- GitHub Issue から新しいエージェントセッションを開始しました。
- **Plan** モードで要件を定義しました。
- **Autopilot** モードで新機能を実装しました。
- コードをレビューしました。
- ブラウザーキャンバスで機能を手動で検証しました。
